# Flint Kit

**Flint 실행부터 튜닝까지, 한곳에서.**

내 Mac의 Flint 실행·성능 튜닝·CLI 연결을 돕는 **독립 로컬 도구**입니다. 새 모델이나 추론 엔진이 아니라 기존 Flint와 rec를 더 쉽게 사용하는 웹 UI이며, 공식 제품이나 제휴 서비스가 아닙니다. 저장소·소스 폴더 이름은 `flint-kit`입니다.

Python 표준 라이브러리로 된 제어 서버와 HTML/CSS/JavaScript 화면으로 구성됩니다. 화면 이동(use-funnel)과 3D 시각 효과(three.js) 번들은 미리 빌드되어 `static/`에 포함되어 있습니다. 계정·클라우드 제어 서비스·텔레메트리·자동 실행 파일 업데이트는 없습니다.

## 배포 방식과 공개 예정 범위

**이 프로젝트는 사용자 Mac에서 실행하는 로컬 앱입니다. Vercel 등에 정적 파일만 배포해서 사용하는 서비스가 아닙니다.** Python 백엔드가 모델 다운로드·검증, 엔진 프로세스 실행·중지, 설정·캐시 관리를 담당하므로 정적 호스팅만으로는 해당 기능이 동작하지 않습니다.

공개 시 권장 구성은 다음과 같습니다.

| 배포 대상 | 역할 |
|---|---|
| GitHub 저장소 | 소스 코드, 실행 안내, 라이선스·출처 및 검증 범위 공개 |
| Vercel 등 정적 호스팅 | 선택적인 소개·설치 안내·스크린샷 사이트 |
| 사용자 Mac | Python 제어 서버, 웹 UI, 추론 엔진과 모델 실행 |

사용자는 저장소를 **clone하거나 소스 ZIP을 다운로드·압축 해제**한 뒤, 해당 디렉터리에서 `python3 run.py`를 실행하고 로컬 주소에 접속합니다. 반드시 Git을 설치하거나 clone해야 하는 것은 아닙니다. 엔진과 모델은 첫 실행 후 화면에서 별도로 준비하며, 소스에 포함되지 않습니다. 향후 설치형 로컬 패키지를 제공할 수 있지만 현재 제공되는 방식은 소스 실행입니다.

공개 안내 사이트에서 사용자의 로컬 엔진을 직접 제어하는 기능은 제공하지 않습니다. 현재 제어 API는 같은 로컬 Origin만 허용하며, 외부 사이트 연결을 위해 CORS·Host·Origin 검사를 해제해서는 안 됩니다.

**현재는 로컬 테스트 단계이며, Git 저장소 연결·업로드·공개 배포는 전체 테스트를 마친 뒤 별도로 진행할 예정입니다.** 공개 전에는 배포 파일과 라이선스·NOTICE·모델 이용 조건을 다시 확인하고, 키·사용자 데이터·로그·모델·실행 바이너리가 포함되지 않았는지 점검해야 합니다. 아직 실행하지 않은 전체 튜닝과 실제 외부 CLI 호환성 시험은 아래 검증 범위와 구분해 안내합니다.

## 실행

`python3 run.py`는 **로컬 웹서버를 시작하는 명령**입니다. Node.js 프로젝트의 `npm run dev`와 같은 진입점이며, 별도의 Python 설정 스크립트를 실행하라는 의미가 아닙니다. 서버는 Python 표준 라이브러리만 사용하고 화면 번들은 미리 빌드되어 포함되므로, 실행에는 `npm install`, `pip install`, 프런트엔드 빌드가 필요 없습니다.

저장소를 clone하거나 소스 ZIP을 압축 해제한 뒤 해당 디렉터리에서 **Python 3.10 이상**으로 실행하세요:

```sh
python3 run.py
```

브라우저에서 **http://127.0.0.1:11539** 를 엽니다. 추론 API는 별도 **127.0.0.1:11540**을 기본 사용합니다. 웹 포트가 겹치면 `python3 run.py --port 11549`로 지정할 수 있습니다. `localhost`나 다른 호스트 이름은 의도적으로 거부합니다.

이후 **엔진 설치·모델 다운로드/검증·추론 서버 시작/중지·설정·캐시 관리·튜닝·CLI 연결은 웹 GUI에서 진행**합니다. 로컬 인증 키도 웹서버 첫 실행 시 사용자별로 자동 생성하므로 직접 입력하거나 설정할 필요가 없습니다. 키는 저장소에 포함되지 않습니다.

웹서버 실행과 모델 실행은 별개입니다. 위 명령만으로 모델 다운로드나 추론 엔진이 자동 시작되지는 않습니다. 웹 GUI의 **서버 시작** 버튼은 모델을 메모리에 올리는 추론 서버를 시작합니다. 생성한 외부 CLI 실행기를 터미널에서 실행하는 과정은 별도이며, 웹앱이 CLI를 자동 실행하지는 않습니다.

웹 서버를 끄려면 실행한 터미널에서 `Ctrl+C`를 누릅니다. 정상 종료 시 이 컨트롤러가 시작한 엔진도 종료합니다. 창/탭을 닫는 것만으로 서버는 꺼지지 않습니다. 설치 상태·설정·모델은 유지됩니다. 로그인 자동 시작이나 전역 셸 프로필 변경은 하지 않습니다.

서버를 재시작하면 기존 탭은 조회 요청에서만 로컬 세션을 다시 받습니다. 설치·삭제 같은 변경 요청은 자동 재전송하지 않습니다.

### 처음 준비하기

1. **엔진 & 모델 → 공식 다운로드 설치**: GitHub 공식 릴리스에서 고정 버전 rec를 다운로드하고 SHA-256을 확인한 뒤, 전용 데이터 폴더에 런타임과 Apache-2.0 Python overlay를 설치합니다. 기존 `~/.local/share/rec/models`에 완전한 Flint 모델이 있으면 먼저 APFS 복제로 가져오고 설치 후 `rec doctor`로 사본을 검증합니다. 다른 앱 설치는 필요하지 않습니다.
2. **가져오기 / 다운로드 / 이어받기**: 기존 rec 모델이 있으면 같은 복제·검증 흐름을 사용하고, 없으면 모델 가중치 약 22.57GB(21.02GiB)를 다운로드합니다. 런타임·캐시용 추가 여유 공간도 필요합니다. 이미 시작한 Flint Kit 다운로드는 보존하고 같은 버튼으로 이어받습니다.
3. **무결성 검증**으로 `rec doctor`를 실행하고 모델 파일의 SHA-256을 확인합니다.
4. **상단 고정 대시보드 → 서버 시작**. 실제 준비 완료가 확인된 후 클라이언트를 연결합니다. 설정 변경·캐시 삭제·설치 작업은 서버를 중지한 상태에서만 허용합니다.

시작 전에 모델의 rec 검증 기록과 파일 식별 정보/크기/수정 시간이 일치하는지 확인합니다. 불완전하거나 변경된 모델이면 명시적인 무결성 검증을 요구합니다. `rec serve`의 암묵적 파일 재다운로드를 막기 위해 시작 프로세스에는 외부 HTTP 프록시 차단 설정도 적용합니다. 실제 다운로드는 다운로드 버튼에서만 허용합니다.

모델 가져오기는 macOS `clonefile`을 사용해 같은 APFS 볼륨의 데이터 블록을 공유하는 독립 사본을 만듭니다. 원본 모델·rec 설정·키는 변경하지 않고, 원본의 inode 기반 `verified.json`도 복사하지 않습니다. 사본을 변경하면 추가 공간을 사용할 수 있으므로 “영구적으로 용량이 들지 않음”을 보장하지 않습니다. 복제 불가 볼륨·불완전한 원본·심볼릭 링크·여러 모델의 모호한 선택은 명시적으로 거부하며, 큰 일반 복사나 다운로드로 몰래 전환하지 않습니다. 실패/취소한 임시 사본은 정리하고 기존 Flint Kit 모델/부분 다운로드는 덮어쓰지 않습니다.

모든 설치·다운로드·연동 생성·캐시 삭제 버튼에는 확인 단계가 있습니다. 네트워크 다운로드는 사용자가 선택할 때만 수행합니다. 패치 설치기는 지원 하드웨어(Apple Silicon M4 Pro/Max, M5 Pro/Max, RAM 48 GiB 이상)와 디스크 여유를 확인합니다. 튜너는 실행 중인 Mac을 읽어 기본값과 worker 후보를 계산합니다. 지원 칩이라는 사실이나 계산된 후보라는 이유만으로 안정성·성능 향상을 보장하지 않습니다.

**macOS 15 이상**이 필요합니다. 15 미만이거나 버전을 읽지 못하면 설치·모델 준비·엔진 시작·튜닝을 시작하기 전에 이유를 표시하고 거부합니다. 웹 화면은 열려서 상태·오류를 확인할 수 있고, 실행 중인 소유 엔진의 중지는 허용합니다. 별도의 첫 실행 인증/질문 게이트는 없습니다.

## 상시 대시보드와 상태 확인

서버 시작·중지, 준비 상태, 최근 완료 요청의 생성·입력 처리 속도와 TTFT, 현재 엔진 메모리는 **탭을 바꾸거나 설정을 스크롤해도 상단에 남습니다.** 아래 설정 영역만 따로 스크롤하며, 작업 중 취소와 오류 요약도 상단에서 확인합니다. 연결이 끊기면 이전 조회값임을 표시하고 서버 제어 버튼을 비활성화합니다.

**상태 & 로그**에서 요청별 기록을 펼쳐 완료 시각·상태·입력/출력/재사용 토큰·TTFT·전체 시간·입력/생성 속도를 봅니다. 최근 최대 60줄/100KB의 수치 기록을 사용하며 이전 실행과 튜닝 요청도 포함될 수 있습니다. 속도는 진행 중 스트리밍의 실시간 속도가 아니라 **최근 완료 요청의 측정값**입니다. 입력 처리 속도는 실제 `prefilled_tokens / prefill_seconds`이며 없는 수치는 추정하지 않습니다. 런타임이 `cancelled_or_failed`로 남긴 기록은 취소와 실패를 구분할 수 없으므로 그대로 안내합니다.

메모리는 `/bin/ps`로 컨트롤러가 소유한 엔진과 자식 프로세스의 RSS를 최대 5초에 한 번 읽습니다. RSS 합계는 공유 메모리를 중복 집계할 수 있고 MLX 할당량·Mac 전체 메모리 압력과는 다릅니다. 관측 최대 RSS는 이번 실행의 샘플 최댓값이지 순간 피크 보장이 아닙니다. 최근 완료 요청의 MLX 피크는 별도로 표시하며 이전 실행 기록일 수 있음을 안내합니다. 중지/조회 실패 시 현재 메모리를 0으로 추정하지 않습니다.

오류 요약은 최근 `engine.log` 최대 64 KiB의 알려진 오류 흔적을 분류합니다. 엔진을 새로 시작하면 이전 로그는 분류 범위에서 제외하며, 웹 서버 재시작 직후에는 기존 로그가 포함될 수 있습니다. 오류 흔적 줄 수는 실제 오류 횟수가 아니고, 분류 결과가 없다고 정상 동작을 보장하지 않습니다. 원문·traceback·요청/응답·API 키는 이 요약에 노출하지 않습니다. 모니터링은 런타임 재설치 없이 웹 서버 재시작으로 적용됩니다.

### 화면 이동과 시각 효과

화면 이동은 [use-funnel](https://use-funnel.slash.page/ko/docs/overview)(`@use-funnel/browser`)로 관리합니다. 현재 화면은 주소의 `?flint-workspace.step=` 값에 남으므로 **브라우저 뒤로/앞으로 가기, 새로고침, 주소 공유**가 그대로 동작하고, 뒤로 가면 이전 화면의 스크롤 위치를 복원합니다. 알 수 없는 화면 값은 엔진 & 모델 화면으로 바로잡습니다. React 화면 이동이 시작되지 못하면 기존 방식의 탭 전환으로 동작합니다.

대시보드의 기존 네 카드 안에 **생성 속도·입력 처리 속도·TTFT 시간대별 막대 차트**와 **메모리 사용량 바**를 표시합니다. 차트의 가로축은 시간입니다. 공통 **차트 단위** 선택기로 세 차트를 함께 전환합니다. **5초 단위는 약 1분, 1분 단위는 약 12분, 기본 5분 단위는 약 1시간**을 보여 줍니다. 시계 기준으로 정렬된 12칸을 오래된 순서에서 지금으로 표시하며, 마지막 칸은 아직 진행 중인 구간입니다. 각 칸은 해당 시간대에 완료된 요청을 웹 서버가 집계한 값입니다. 화면은 2초마다 조회하며, 5초 보기 역시 진행 중 토큰의 실시간 속도가 아니라 **완료된 요청의 측정값**입니다.

선택은 이 브라우저의 로컬 저장소에 기억하므로 새로고침 후에도 유지됩니다. 제거된 15분 단위가 저장되어 있다면 기본 5분 단위로 변경하고 안내합니다. 저장소가 차단되면 이를 안내하고 현재 화면에서만 적용합니다. 단위 변경은 읽기 전용 조회이며 **엔진 재시작·튜닝·설정 변경 없이** 기존 기록을 다시 집계합니다. 집계 중에는 이전 시간축을 흐리게 유지하고, 빠르게 선택을 바꿔도 마지막 선택만 반영합니다. 업데이트 후에는 웹 서버를 한 번 재시작해야 새 단위를 지원하는 선택기가 활성화됩니다.

- 생성 속도는 생성 시간으로 가중한 평균이며, 한 토큰만 생성해 속도를 잴 수 없는 응답은 제외합니다.
- 입력 처리 속도는 새로 처리한 입력 토큰 ÷ 처리 시간이며, 캐시로 처리할 입력이 없던 요청은 제외합니다.
- TTFT는 구간 안 요청의 중앙값입니다.

요청이 없던 구간은 빈칸으로 남고, 칸에 마우스를 올리면 `HH:MM–HH:MM · 요청 N개 · 값`이 보입니다. **5초 보기에서는 `HH:MM:SS–HH:MM:SS`로 초까지 표시**합니다. 막대 높이는 각 차트의 최댓값에 맞춰 0부터 선형 비례하므로 세 차트의 막대 높이를 서로 직접 비교하지 않습니다. 선택한 범위에 완료한 요청이 없으면 '요청 없음', 요청은 있으나 측정값이 없으면 '측정값 없음'을 표시합니다. 이번 엔진 실행의 요청만 집계하므로 엔진을 다시 시작하면(튜닝 포함) 차트도 새로 시작하며, 이전 실행 수치는 상단 숫자에 남을 수 있지만 차트에는 섞지 않습니다. 시간대별 집계를 지원하지 않는 이전 웹 서버에서는 '서버 재시작 필요'가 표시됩니다.

메모리 바는 시간 기록이 없는 현재값으로, 엔진 RSS 합계 / Mac 물리 메모리 비율입니다. 총 용량이나 현재 측정값을 모르면 채우지 않습니다.

three.js는 앱의 라임 액센트에서 짙은 녹색으로 이어지는 그라데이션 막대를 그리는 데만 사용합니다. 색상은 `static/style.css`의 차트 토큰 한 곳에서 정하며 CSS 대체 막대와 WebGL 막대가 같은 값을 씁니다. **새 데이터로 높이가 바뀔 때만 280ms 전환**하고 계속 흐르거나 회전하는 효과는 없습니다. 사용 안내 화면에는 애니메이션이 없습니다. 차트가 화면 밖이거나 브라우저 탭이 숨겨졌을 때는 그리지 않고, **동작 줄이기** 설정에서는 즉시 갱신합니다. WebGL을 쓸 수 없으면 같은 데이터를 CSS 막대로 표시합니다. 연결이 끊기면 마지막 차트를 흐리게 남기고 메모리 사용량 바는 숨깁니다. 차트의 접근성 설명과 **상태 & 로그**의 표에서도 실제 수치를 확인할 수 있습니다.

## 데이터와 키

## 실제 측정 튜닝

**worker와 chunk는 서로 다른 지표를 사용하는 분리 단계**로 선택합니다. 먼저 현재 chunk에서 하드웨어 기반 worker 후보를 비교하고, 선택한 worker에서 고정 chunk 후보 `[1024, 2048, 4096]`을 비교합니다. 화면과 실제 튜너는 같은 후보 생성 함수를 사용하며 worker N개 + chunk 3개 시도를 안내합니다. 변경 후보가 있으면 **측정 기준과 최종 조합 재측정 2회**를 추가합니다. 기준은 보통 원래 설정이며, 시작 실패로 rec 기본값을 사용했으면 이를 명시합니다. 기본값이 원래 탐색 목록에 없으면 시험 1회를 추가하고, 이미 있으면 순서만 앞당겨 중복 측정하지 않습니다. 멈춘 후보의 상위 값은 미측정으로 기록합니다. 변경 후보가 없으면 최종 재측정 2회를 생략하고 총 시도 수도 줄입니다. 후보가 많은 Mac은 오래 걸릴 수 있고 취소할 수 있습니다. worker를 바꿀 때 `device.py`뿐 아니라 **M4 filtered sampler 수정이 있는 `kernels/sampling.py`도 포함**합니다.

기본값과 worker 조합 탐색 방식은 유지합니다. 기본값은 신규 데이터 폴더의 출발점이며, 튜닝 결과를 다른 Mac의 공통 기본값으로 사용하지 않습니다. 기존 문맥·출력 상한·샘플링·캐시 사용 여부를 자동 변경하지 않습니다.

### 하드웨어 감지와 후보 계산

튜닝 화면에는 판단에 필요한 **칩·GPU 코어·통합 메모리(GiB)·데이터 볼륨 여유 디스크(GiB)·요건 통과/미충족**만 표시합니다. 칩은 지원 여부·기본 workers/chunk, GPU 코어는 worker 후보, 메모리는 48 GiB 요건과 측정 출처, 디스크는 설치 여유 요건과 캐시 용량 선택에 사용합니다. CPU 성능/효율 코어 수와 `hw.model`은 원본에서도 튜닝 결정에 사용하지 않으므로 수집·표시하지 않습니다. macOS 15 이상 여부는 실행 요건에 표시하며, 상세 버전은 **측정 결과의 환경 기록**에 남깁니다. 결과에는 칩·GPU 코어·메모리·macOS를 기록하며 현재 환경과 다르면 재측정을 권합니다. 기존 결과에 기록이 없으면 단순히 “측정 환경 기록 없음”으로 표시합니다.

감지 소스는 절대경로 `/usr/sbin/sysctl -n hw.optional.arm64`, `machdep.cpu.brand_string`, `hw.memsize`, `/usr/sbin/ioreg -rc AGXAccelerator -d 1`의 `gpu-core-count`입니다. 셸 없이 제한된 환경 변수와 5초 timeout으로 실행하며 포맷을 검증합니다. 성공한 값은 프로세스 수명 동안 캐시하고, 읽지 못한 값만 60초 간격·총 3회까지 재시도합니다. 폴링마다 명령을 실행하지 않습니다. 실패한 값은 이유와 함께 “알 수 없음”이며, 20 GPU 코어 등으로 추정하지 않습니다. 여유 디스크만 매번 갱신합니다. 원본은 purgeable 공간이 포함될 수 있는 `volumeAvailableCapacityForImportantUsage`를 사용하지만 여기서는 `shutil.disk_usage(data_home).free`를 사용하므로 더 보수적일 수 있습니다.

기본 decode D는 M5 Max 또는 GPU 40코어 이상인 M4 Max에서 76, 나머지는 36입니다. 기본 MLP/head M은 D=76이면 64, 아니면 32입니다. 기본 chunk는 칩이 `Apple M5`로 시작하면 4096, 아니면 2048입니다. 신규 데이터 폴더에만 감지 기반 기본값을 적용하며 저장한 설정은 덮어쓰지 않습니다. 감지 실패로 기본값을 결정할 수 없으면 보수적인 36/32/32·2048(확인된 M5 칩은 4096)에서 시작하되, 하드웨어를 확인했다는 뜻은 아닙니다.

원본 앱에서 복원한 후보 수식은 다음과 같습니다. C는 감지한 GPU 코어 수이며, 반올림은 양수의 ties-away(half-up)입니다.

- decode 상한 `max(D, (int(C * 1.9) // 4) * 4)`, 시작값 `max(32, floor(C / 4 + 0.5) * 4)`. 시작값부터 8씩 증가한 값과 상한·D를 합쳐 상한 이하로 중복 제거·정렬합니다.
- MLP 상한 `max(M, (int(C * 1.6) // 4) * 4)`. `[32, 64]` 중 상한 이하만 사용하며 MLP ≤ decode인 `[decode, mlp, mlp]` 조합만 후보입니다. 허용 저장값은 이 격자·해당 칩 기본값·복구용 rec 기본값 `36/32/32`의 합집합입니다. 큰 GPU의 정상 탐색 격자에 `36/32/32`를 추가하지는 않으며 현재값이거나 시작 복구에 필요할 때만 측정합니다.
- 예: M4 Pro 20코어 → decode `[32,36]`, MLP `[32]` (2조합). M4 Max 32코어 → decode `[32,36,40,48,56,60]`, MLP `[32]` (6조합). M4 Max 40코어 → decode `[40,48,56,64,72,76]`, MLP `[32,64]` 중 MLP ≤ decode (9조합). chunk 3개는 감지 결과가 아닌 고정 탐색 값입니다.

**원본 앱 수식으로 계산한 후보이며, 이 칩/코어 조합은 우리가 실측 검증 전이고 이 Mac에서 직접 측정해 채택합니다.** 독립 실측 수용 범위는 M4 Pro 20 GPU 코어의 현재값 시험입니다. 다른 칩/코어 전체 후보와 M5의 비기본 workers는 독립 실측하지 않았습니다. M4 Max 기본 76 workers는 모든 worker 동시 상주가 필요하므로 코어 40개 이상에서만 사용합니다.

튜닝은 macOS 15 이상·Apple Silicon·지원 칩·48 GiB 이상 메모리·읽을 수 있는 GPU 코어가 필요하며 미확인/미충족 시 엔진을 건드리기 전에 이유와 함께 거부합니다. 디스크 요건(모델 있으면 10 GiB, 없으면 32 GiB)은 표시용이며 튜닝 차단 조건은 아닙니다. 다른 Mac에서 가져온 저장 workers가 현재 허용 범위 밖이면 자동 교정하지 않고 시작·튜닝을 거부합니다. 코어 미확인 등으로 유효성을 판단할 수 없으면 기존 설정을 보존하고 시작은 경고와 함께 허용하되 새 비기본 workers 저장과 튜닝은 제한합니다. 웹 서버가 구버전 상태를 반환하면 UI는 재시작 안내만 표시하며 기존 튜닝 진행·결과·취소는 유지합니다.

### 측정·채택·복원 규칙

- 현재값을 먼저 측정합니다. 속도 측정 전에 동일한 greedy 요청을 **3회** 보냅니다: temperature 0, seed 0, 최대 96토큰, 90초. 응답 `message` 객체의 정렬 JSON SHA-256이 모두 같아야 기준 응답으로 사용합니다. 다르면 재현성을 확인할 수 없다는 오류로 중단하고 원래 설정·실행 상태를 복원합니다. 검증을 생략하고 채택하지 않습니다. 이후 각 탐색 후보에도 별도 greedy 요청을 보내 기준 해시와 비교합니다. 이것은 출력 동등성 검증이지 의미적 정답이나 seed 지원의 증명은 아닙니다.
- 모델은 이 짧은 greedy 시험에서 최종 `content` 없이 `reasoning`만 반환할 수 있습니다. 유효한 role/usage를 확인하고 **reasoning을 포함한 전체 message 객체**를 해시하며, 본문은 저장하지 않습니다. max_tokens 1 prefill 시험은 보이는 텍스트 없이도 토큰 처리 및 수치 기록이 있으면 정상입니다.
- 속도 시험은 temperature 0.6, 최대 256토큰입니다. 짧은 입력 3회(각 60초), 긴 입력 3회(각 240초)의 **metrics `decode_tokens_per_second` upper median**을 구하고 두 중앙값의 산술평균을 점수로 사용합니다.
- 긴 입력은 확인된 calibration filler 생성 규칙의 **nominal 32,000**을 사용하며 같은 입력으로 max_tokens 1 preload를 수행합니다. 별도 nominal 8,000 prefill 입력에 max_tokens 1/120초, 매번 새 UUID로 3회 진단합니다. nominal은 tokenizer로 측정한 실토큰 수가 아니며 문맥 초과 시 오류를 숨기지 않습니다.
- chunk 선택에는 decode 점수가 아니라 위 fresh prefill 3회 속도의 upper median을 사용합니다. 이 앱의 prefill 속도 정의는 metrics의 실제 `prefilled_tokens / prefill_seconds`입니다. worker/청크 모두 각 단계 현재값보다 엄격히 3% 초과 개선되어야 채택합니다.
- **시작 재시도는 튜닝의 각 시험에만 제한합니다.** 설정·하드웨어·다른 엔진·포트·설치·모델/실행 파일 무결성 검사를 통과해 자식 엔진을 실행한 뒤 준비 전 종료되거나 준비 제한 시간(300초)을 넘긴 경우에만, 소유 엔진을 정리하고 1초 뒤 한 번 더 시작합니다. 두 번째 실패는 해당 시험의 실패입니다. 이런 오류가 실제로 일시적인지는 단정하지 않으며, 최초 원인과 시도 횟수를 로그·시험 결과에 남깁니다. 사전 검사, 프로세스 실행 자체의 오류, 응답 불일치, 잘못된 metrics, 취소는 재시도하지 않습니다. 기본값으로 몰래 바꾸거나 다른 프로세스를 종료하지 않습니다.
- **전체 튜닝의 시작 복구:** 현재 workers가 두 번 모두 시작하지 못한 경우에만 rec 기본 workers `36/32/32`로 별도 기준 측정을 시도합니다. chunk·문맥·샘플링 등 저장 설정은 바꾸지 않습니다. 이미 rec 기본 workers라면 같은 시험을 반복하지 않으며, 현재값만 측정·사전 검사 실패·응답/속도 측정 실패·취소에서는 전환하지 않습니다. 기본값에서도 greedy 3회 재현성과 모든 속도 측정이 통과해야 진행합니다. `fallback`·`measurement_baseline`에 원인과 실제 비교 기준을 기록합니다.
- **멈춘 후보 건너뛰기:** 시작이 두 번 실패했고 그중 준비 시간 초과가 있었을 때만 적용합니다. worker 격자는 같은 chunk에서 실패한 `[D,M,H]`보다 모든 성분이 같거나 크고 하나 이상 큰 후보만 생략합니다. MLP가 낮아지는 등 비교할 수 없는 조합은 계속 측정합니다. chunk 단계에서는 같은 workers의 더 큰 chunk만 생략합니다. 준비 전 종료만 발생한 경우·추론 timeout·답변 불일치에는 생략하지 않습니다. 같은 실행 안에서만 사용하는 보수적 휴리스틱이며 모든 상위 후보가 실제로 실패한다는 증거는 아닙니다. 생략한 후보는 점수 없이 `skipped=true`와 이유를 기록하며 성공 후보로 취급하지 않습니다.
- **최종 조합 검증:** worker 또는 chunk가 바뀌는 후보를 찾으면, 탐색 초기 점수를 재사용하지 않고 측정 기준 worker·chunk 조합을 새로 시작해 재측정한 뒤 최종 후보 조합도 새로 시작해 같은 방식으로 재측정합니다. 양쪽 모두 greedy 3회가 최초 기준 해시와 일치해야 하며, 워밍업·짧은/긴 생성 각각 3회·fresh prefill 3회를 수행합니다. 비교 조건은 동일한 측정용 문맥과 SSD 캐시 꺼짐입니다.
- 최종 비교에서 **측정 기준 대비 worker가 바뀌면 생성 속도, chunk가 바뀌면 읽기 속도가 각각 엄격히 3% 초과 개선**되어야 합니다. 둘 다 바뀌면 두 지표 모두 통과해야 합니다. 변경하지 않은 항목의 지표도 **3% 넘게 하락하면 거부**합니다(정확히 3% 하락은 허용). 이 3% 하락 허용 폭은 측정 변동을 고려한 독립 정책이며, 성능 회귀가 없다는 보장은 아닙니다.
- 기본값으로 복구했다면 **원래 설정 대비 성능 개선을 주장하지 않습니다.** rec 기본값 자체를 제안하는 경우에도 독립 재시작 2회의 최종 측정을 수행하고 두 지표의 3% 초과 하락을 거부합니다. 성공 시 `recovered=true`로 복구 제안임을 구분하고 사용자 확인 후에만 적용합니다. 기본값에서 다른 성능 후보를 찾았으면 3% 개선 비교도 그 기본값을 기준으로 합니다. 복구의 최종 검증이 실패하면 캐시를 포함해 어떤 제안도 남기지 않습니다.
- 기본값 복구가 아닌 일반 튜닝에서 최종 속도 기준에 미달하면 `verification.state="rejected"`와 이유를 기록하고 worker·chunk는 원래 값으로 유지합니다. 차선 후보를 자동 선택하거나 검증되지 않은 조합으로 부분 적용하지 않습니다. 이 경우에도 별도의 디스크 기준 캐시 용량 제안은 남을 수 있습니다. 반면 최종 응답 검증·측정 자체가 실패하거나 취소되면 전체 작업 실패/취소로 처리하고 **캐시를 포함한 어떤 제안도 남기지 않습니다.**
- 수치는 해당 요청 직전 파일 offset 이후의 **단일 완료 metrics**와 `usage.prompt_tokens` 일치를 확인하여 가져옵니다. wall time 기반 처리량으로 대체하지 않습니다.
- 튜닝 중에는 임시 비밀 헤더로 외부 CLI 추론 요청을 거부하며 SSD 캐시를 끕니다. 한 컨트롤러의 설치·서버·설정·튜닝은 상호 배제됩니다.
- 긴 입력용 문맥은 최소 65,536으로 임시 확장한 동일 조건으로 측정하고 이후 원래 문맥 설정으로 복원합니다. **현재값만 측정** 버튼은 같은 실제 시험을 현재 후보 한 개에만 수행하고 설정은 채택하지 않습니다.
- **전체 자동 튜닝의 문맥·캐시 정책:** Flint Kit은 사용자가 선택한 문맥을 보존합니다. 확인된 원본 문맥 선택지는 `[32768, 65536, 131072, 262144]`입니다. 조사한 phase runner는 calibration key에 기존 Options의 문맥을 사용하지만, 결과 문맥에는 서버 상태의 `maxContext`가 있으면 이를 우선하고 없으면 기존 Options 문맥을 사용합니다. `fill(into:)`는 그 결과를 적용합니다. 이 override 경로와 선택지 목록만으로 최적 문맥 탐색을 단정할 수 없어 별도 탐색을 추가하지 않았습니다. Flint Kit에서는 측정용 임시 확장값이 사용자 문맥을 덮어쓰지 않도록 분리하고 결과에 각각 기록합니다. 원본의 서버 보고값 우선 정책과 동일하다는 주장이 아닙니다.
- worker·chunk 측정이 성공하면 **앱 데이터가 위치한 파일시스템의 현재 여유 디스크**로 캐시 상한을 자동 선택합니다. 예산은 `free_bytes // 5 // (2**30)` GiB이며, `[8, 16, 32, 64, 128, 192, 256, 384, 512]` 중 예산 이하인 최댓값을 선택합니다. 없으면 확인된 규칙대로 최소 8 GiB를 선택하고 화면에 예산 미달을 표시합니다. 예: 여유 80 GiB → 16 GiB, 160 GiB → 32 GiB. 이 용량은 즉시 할당·예약하는 공간이 아니며, 다른 프로그램의 디스크 사용이나 디스크 부족을 방지하지 않습니다.
- 캐시 상한 선택은 성능 점수나 3% 채택 기준과 별개입니다. 성능 후보를 유지하더라도 전체 튜닝이 성공하면 상한을 **제안에 포함**합니다. **SSD 캐시 사용 여부는 유지**하며 자동 활성화하지 않습니다. 현재값만 측정은 문맥·캐시 상한 모두 바꾸지 않습니다. 이 자동 튜닝은 GUI에서 실행하며 별도의 수동 벤치마크 명령은 필요하지 않습니다. Pi 자동 압축 설정은 변경하지 않습니다. 수동 설정은 **설정 & 캐시**에서 가능합니다.
- 현재값의 검증·측정이 실패하면 후보를 채택하지 않습니다. 가장 좋은 유효 후보가 현재값보다 **엄격히 3% 초과** 개선된 경우만 채택합니다. 정확히 3%는 유지합니다.
- 취소·실패 시 기존 설정과 실행 여부를 복원합니다. 복원 실패는 별도 오류로 표시합니다. HTTP 요청 중 취소도 감지하고 소유한 엔진을 종료합니다.
- 측정이 성공해도 제안을 자동 적용하지 않습니다. 튜닝 전 설정과 실행 여부를 복원하고 제안만 `tuning.json`에 대기 상태로 보관합니다. 원본 복원에 실패하면 재시도하며, 재시도도 실패하면 별도의 복원 오류를 남깁니다.
- 최종 설정·결과 파일 저장 실패도 성공으로 표시하지 않습니다. 독점 측정 토큰과 취소 상태는 설정 저장 성공 여부와 무관하게 해제합니다. 원본 설정 복원과 기존 실행 상태 복원을 시도하며, 저장·재시작·실패 결과 재저장 오류를 구분해 알립니다.

### 진행 / 결과 팝업과 확인 후 적용

튜닝 시작 시 진행 팝업이 열립니다. 워커/rec 기본값 기준/읽기 묶음/최종 비교(측정 기준·후보 조합) 단계, 후보 시험 n/전체 수, 기준 응답 재현성·엔진 시작과 제한된 재시도·워밍업·출력 검증·짧은/긴 생성·읽기 반복, 경과 시간을 표시합니다. 완료한 후보는 즉시 목록에 쌓이며, 완료된 후보 소요시간이 있을 때만 예상 잔여 시간을 표시합니다. 재시도 횟수와 이전 시작 실패 원인도 시험별로 남깁니다. 생략한 후보는 진행률에는 포함하지만 소요시간 평균에는 포함하지 않습니다. **닫기 또는 Esc는 팝업만 닫고 측정을 계속**합니다. 튜닝 구간의 “진행 / 결과 보기”로 다시 열며, 취소는 별도 버튼으로 원본 복원을 요청합니다. 원본 복원이 시작된 뒤의 추가 취소는 복원 자체를 끊지 않도록 거부합니다.

완료 화면은 실제 속도의 전/후, 접이식 “값마다 잰 것”, 워커·읽기 묶음·문맥·캐시 설정 비교, 측정 환경을 표시합니다. 최종 비교가 진행되면 요약 속도는 **`verify_baseline`과 `verify_candidate`의 재측정값**을 사용합니다. 실패한 시험의 부분 측정값은 요약에 사용하지 않습니다. 초기 탐색값과 최종값은 별도 행으로 남기며, 미달 후보는 “최종 채택 보류”로 표시합니다. 캐시 용량만 제안할 수 있다는 점도 구분합니다.

최종 비교가 없거나 이전 결과인 경우에는 기존처럼 워커 단계의 생성 점수와 읽기 묶음 단계의 prefill 점수를 표시하고, 최종 조합 통합 측정값이 아니라는 경고를 유지합니다. 기준 응답 반복 검증이 없는 이전 결과도 명시합니다. 3% 채택 기준 근처의 개선은 실행마다 달라질 수 있으며 성능 향상을 보장하지 않습니다. 무변경은 “채택 기준을 넘는 개선이 없습니다.”로 표시합니다. 후보가 더 빠르더라도 개선폭이 3% 이하면 유지될 수 있으므로 현재값이 가장 빠르다고 단정하지 않습니다. 현재값 단독 시험은 “현재값 측정 완료”로 표시합니다.

적용 요청 거부와 연결 오류는 팝업 안의 경고 영역에도 표시합니다. 이 경고는 조회·새로고침이나 팝업 닫기로 없어지지 않으며 새 측정 결과 ID를 받거나 적용 재시도를 시작할 때만 초기화합니다. 요청 거부는 제안을 적용하거나 대기 상태를 해제하지 않습니다.

**가정(사용자 확인 전 코디네이터가 정한 정책):** 측정 후 자동 적용 대신 확인 후 적용을 사용합니다. “닫기”는 상태 변화 없이 팝업만 닫고, “나중에 적용”은 제안을 보류합니다. **“적용하고 다시 시작”은 저장된 제안만 적용하며 엔진이 꺼져 있었어도 시작**합니다. 이 가정은 사용자 결정에 따라 코드 정책을 되돌릴 수 있으며, 이번 구현이 원본의 전체 상태 기계와 같다는 뜻은 아닙니다.

적용 API `POST /api/tune/apply`는 `{"tuning_id":"측정 ID"}`만 받으며 브라우저가 임의 설정값을 보낼 수 없습니다. 기존 루프백 Host/Origin·세션·CSRF 경계를 그대로 적용합니다. 적용 전 대기 상태/ID, 현재 저장 설정과 측정 전 설정의 일치, 확인 가능한 측정 환경의 일치, 현재 하드웨어의 설정 유효성, 적용 시점 캐시 규칙을 모두 검사합니다. 새 결과는 기준 응답 재현성 통과가 필수이며, worker·chunk 변경 제안은 최종 검증을 통과한 조합 및 실제 측정 기준과도 일치해야 합니다. 디스크 여유가 줄어 제안 캐시 용량을 허용할 수 없으면 “다시 튜닝하세요”로 거부하며 용량을 몰래 줄이지 않습니다. macOS는 15 이상 확인이 필수이며 그 외 환경 일부가 미확인이면 경고를 남기되 설정 유효성 검증은 생략하지 않습니다. 동시 작업·이중 적용은 거부합니다.

적용 중 중지·설정 저장·엔진 시작·결과 저장이 실패하면 원래 설정과 적용 직전 실행 상태의 복원을 각각 시도하고 실패를 명시합니다. 제안은 대기 상태로 남기며, 복원까지 실패했다면 오류를 해결해야 합니다. 성공한 경우에만 `applied=true`, 실제 적용 설정, 캐시 적용 여부를 결과 파일에 atomic하게 기록합니다. 대기 제안은 웹 서버 재시작 후에도 유지됩니다. 이전 자동 적용 방식의 결과(새 필드가 없는 기록)는 **“이전 방식으로 적용됨”**으로 표시하며 대기 제안으로 취급하지 않습니다.

확인 후 적용은 `capabilities.tune_apply`, 검증 강화 흐름은 `capabilities.tune_reliability`로 판별합니다. 새 화면과 구버전 백엔드 조합에서도 인라인 결과·팝업·취소는 유지합니다. `tune_apply`가 없으면 적용 버튼 없이 기존 자동 적용 안내를 표시하고, `tune_reliability`가 없으면 새 검증을 수행한다고 주장하지 않고 서버 재시작을 안내합니다. 이전에 만들어진 대기 제안은 새 검증 기록이 없다는 경고와 함께 기존 적용 흐름을 유지합니다. 새 기준으로 확인하려면 다시 튜닝해야 합니다. 기존 API 필드는 유지하며 `baseline_check`, `verification`, 시험별 `answer_hashes`·`decode_score`·`start_attempts`·`start_errors`를 추가합니다. 응답 본문이나 키는 이 기록에 저장하지 않습니다.

### 환경 / 문맥별 기록

완료·실패·취소 결과는 `tuning-history/<측정 ID>.json`에 개별 보관합니다. 다음 튜닝 전에 기존 마지막 결과도 보관하고 `tuning.json`은 최신 진행/적용 대기 결과로 유지합니다. 적용 성공/실패 상태도 같은 기록에 반영하며, 저장 오류를 성공으로 숨기지 않습니다. 기록에는 속도 수치·검증 해시·설정·실패 원인만 저장하며 응답 본문·API 키는 넣지 않습니다.

구분 키는 **칩·GPU 코어·메모리·macOS 버전·사용자가 설정한 문맥**의 조합입니다. 32K 설정에서 측정용으로 임시 확장한 64K가 키를 덮어쓰지 않습니다. 일련번호나 장치 UUID를 수집하지 않으므로 같은 사양/OS의 Mac은 같은 그룹이 될 수 있습니다. 데이터 폴더를 자동으로 다른 Mac과 동기화하지 않습니다.

**성능 튜닝 → Mac 환경 / 문맥별 측정 기록**에서 최근 100개 기록을 선택해 읽을 수 있고 이전 파일은 자동 삭제하지 않습니다. 보관 기록은 읽기 전용으로 현재 진행/대기 제안을 바꾸거나 즉시 적용하지 않습니다. 현재 환경에서 다시 측정한 제안만 기존 적용 흐름으로 사용합니다. 조회 API `GET /api/tune/history/<측정 ID>`도 루프백 Host/Origin·세션·CSRF를 요구하며 서버에 알려진 UUID만 받습니다. `capabilities.tune_recovery`/`tuning_history`가 없는 구버전 서버에는 재시작 안내를 표시합니다.

**독립 구현의 한계:** 확인된 원본의 개별 규칙과 worker/chunk 분리 지표를 재현한 것이며, 구체적인 시험 배치·재시도·취소·복원 상태 기계와 prefill 속도 계산식은 독자 구현입니다. 전체 원본 알고리즘/성능/품질의 동일성을 주장하지 않습니다. GPU 온도·메모리 압력·다른 앱 사용이 측정에 영향을 줍니다. 전체 단계 측정은 수분~수십 분이 걸릴 수 있습니다.

**정적 근거:** 분석 대상 0.1.8 build 9 native SHA-256 `edd3c3b324e5e6da19e2ee45a29dfa3ef71497b252829204fc6a83726bb968f0`에서 `Calibration.cacheGB(freeDisk:)` (`0x1000c6060`), `Options.cacheGBs`의 정수 배열 (`0x100175ed8`), `Options.contexts`의 정수 배열 (`0x100175920`), runner의 기존 Options 복사 (`0x1000260c4`), 결과용 문맥 읽기 (`0x100028238`), `CalibrationRun.fill(into:)`의 문맥·용량 적용 (`0x100035d34` 이후)을 확인했습니다. `Machine.calibrationKey(context:)`는 문맥별 결과 식별 근거이지 문맥 자동 탐색의 증거는 아닙니다. 네이티브 실행 코드·디컴파일 결과는 이 저장소에 포함하지 않습니다.

## 선택적 CLI 연동

새 설치의 기본 문맥 한도는 65,536토큰(64K)입니다. 실제 문맥이 길어지면 메모리 사용량과 처리 시간이 증가합니다. 기존에 저장한 문맥 설정은 자동 변경하지 않습니다.

| 도구 | 연결 방식 |
|---|---|
| Claude Code | 별도 `CLAUDE_CONFIG_DIR` 및 프로세스 전용 endpoint/token/model 환경 변수 |
| Codex CLI | 명령 인자 `model_provider`, `/v1/responses`, env key |
| opencode | 기존 사용자 설정에 `provider.flint-local` 추가 → 평소 `opencode`의 `/models`에서 선택 |
| Pi | 기존 `models.json`에 `providers.flint-local` 추가 → 평소 `pi`의 `/model`에서 선택 |

### Pi / opencode: 다른 모델과 함께 사용

클라이언트 화면은 네 개의 작은 카드로 구성됩니다. 등록 상태와 주요 버튼은 바로 보이고, 긴 설명·실행 명령·설정/백업 경로·이전 격리 실행기는 각 카드의 **사용법 · 경로 · 관리**에서 펼쳐봅니다. 펼친 상태는 주기적인 상태 갱신 중에도 유지됩니다. 작은 화면에서는 카드를 한 열로 표시합니다.

**클라이언트 → 기존 CLI에 Flint 추가**에서 대상 경로·주소·문맥·출력 한도를 확인합니다. 변경 전에 비공개 백업을 만들고, 기존 모델·기본 모델·인증·프로젝트 설정을 유지한 채 `flint-local/flint`만 추가합니다. Pi의 기본 위치는 `~/.pi/agent/models.json`, opencode는 `~/.config/opencode/opencode.json`입니다. 기존 `opencode.jsonc`가 있으면 그 파일을 사용하며 다른 항목의 주석·서식·후행 쉼표를 보존합니다.

Pi는 `!/bin/cat '<키 파일>'`, opencode는 `{file:<키 파일>}`로 로컬 키를 참조합니다. 키 원문을 사용자 설정이나 브라우저에 복사하지 않습니다. Pi는 `/model`을 다시 열면 설정을 다시 읽고, opencode는 다시 시작한 뒤 `/models`에서 **Flint Kit**을 선택하세요. 이전에 등록한 항목은 **Flint Local**이라는 표시 이름으로 계속 사용할 수 있으며, **Flint 설정 갱신**을 확인하면 같은 provider ID를 유지한 채 새 표시 이름을 적용합니다. 실행 중인 백그라운드 서비스가 설정을 유지하는 opencode 버전에서는 `opencode reload`로 다시 읽습니다. Flint 사용 전에는 대시보드에서 엔진을 시작해야 합니다. 다른 모델은 기존 서버·계정으로 계속 사용할 수 있으며, 같은 대화에서 원격 모델로 전환하면 그 서비스로 대화가 전송될 수 있습니다.

포트·문맥·출력 한도를 변경하면 연결 카드에 **Flint 설정 갱신** 안내가 나타납니다. 확인 후 해당 항목만 갱신합니다. **Flint 연결 해제**는 앱이 추가한 항목만 제거하며, 연결 후 다른 모델·설정을 수정했더라도 그 변경은 유지합니다. 이후 변경이 없으면 원래 파일을 그대로 복원하고, 새로 만든 파일이면 제거합니다. 백업은 해제 후에도 앱 데이터 폴더에 남습니다. 백업에는 기존 설정의 민감한 값이 포함될 수 있으므로 공개하지 마세요.

동명 provider가 이미 있거나 Flint 항목 자체가 외부에서 수정된 경우 덮어쓰거나 제거하지 않고 오류를 표시합니다. 잘못된 JSON·중복 키·심볼릭 링크·2 MiB 초과 파일·작업 중 감지한 외부 변경도 거부합니다. opencode에 여러 전역 설정 파일 또는 구형 `config.json`이 있으면 하나의 `opencode.json`/`opencode.jsonc`로 정리해야 합니다. `enabled_providers`/`disabled_providers`가 Flint를 차단하면 기존 제한을 우회하지 않고 연결을 거부합니다.

대상 위치는 웹 서버 환경의 `PI_CODING_AGENT_DIR`와 `XDG_CONFIG_HOME`을 반영합니다. 터미널의 환경 변수가 다르거나 프로젝트 설정·`OPENCODE_CONFIG`·`OPENCODE_CONFIG_CONTENT`·관리자 정책이 덮어쓰면 모델 표시가 달라질 수 있습니다. 이 앱은 그런 설정을 자동 수정하지 않습니다. API는 고정된 클라이언트 이름과 추가/제거 여부만 받으며 임의 경로·설정 내용을 받지 않습니다.

### Claude Code / Codex CLI: 별도 명령 유지

Claude Code의 `/model`은 모델 이름을 바꾸지만 `ANTHROPIC_BASE_URL`을 모델별로 전환하지 않습니다. 기존 Claude와 로컬 Flint를 하나의 CLI에서 라우팅하려면 별도 gateway가 필요하므로 이 앱은 이를 추가하지 않습니다. **`claude`는 기존 공식 Claude, `claude-flint`는 로컬 Flint**로 분리합니다. 기존 로그인과 데스크톱 앱은 건드리지 않습니다. 로컬 endpoint를 통한 비-Claude 모델은 Anthropic의 공식 지원 범위가 아닙니다.

`claude-flint` 실행 시 `~/.claude.json`(기존 `CLAUDE_CONFIG_DIR`가 설정돼 있으면 그 안의 `.claude.json`)에서 **온보딩 완료·버전·터미널 키 설정 상태와 이미 신뢰한 폴더의 `hasTrustDialogAccepted=true`만 한 번 가져옵니다.** 대상은 `clients/claude/config/.claude.json`이며, 이미 있는 값(명시적으로 해제한 신뢰 포함)은 덮어쓰지 않습니다. 로그인·API 키·MCP·허용 도구·대화 기록은 복사하지 않고 원본은 읽기만 합니다. 완료 기록은 `clients/claude/onboarding-import.json`에 남겨 이후 신뢰 해제를 다시 되돌리지 않습니다. 원본이 없으면 CLI의 정상 초기 설정을 진행하며, 손상된 JSON/심볼릭 링크/동시 변경은 이유를 알리고 실행을 중단합니다. 이미 승인한 항목만 재사용하므로 새 폴더나 CLI의 새로운 질문까지 생략한다는 보장은 없습니다.

**클라이언트 → 전용 실행기 생성**은 앱 데이터 폴더 안에 실행기를 만듭니다. 실제 CLI 설치·실행, `~/.claude`, `~/.codex`, 로그인 파일, PATH는 수정하지 않습니다. 화면에 나온 실행기의 **전체 경로**를 터미널에서 실행하세요. 경로에 공백이 있으면 따옴표로 감싸세요. 포트·문맥·출력 한도 변경은 실행기를 다시 실행하면 반영됩니다.

실행기는 키 파일을 직접 읽고 준비된 로컬 엔진을 확인합니다. 서버가 없다고 자동으로 다른 엔진을 띄우거나 CLI를 다운로드하지 않습니다. 재생성/복원 전 파일 해시를 확인하며, 이후 사용자 수정이 있으면 복원을 거부합니다. 기존 실행기 내용은 보관 후 복원합니다.

전용 실행기를 만든 뒤 **전용 명령 설치**를 선택하면 `~/.local/bin`에 `claude-flint` 또는 `codex-flint` 링크를 만듭니다. CLI에 전달한 인자도 그대로 전달됩니다. 같은 이름의 기존 파일·심볼릭 링크는 덮어쓰지 않으며, 설치 후 링크가 변경되면 제거를 거부합니다. **전용 명령 제거 → 실행기 제거** 순서로 되돌리세요. 이전에 만든 `pi-flint`/`opencode-flint`도 계속 작동하며 카드 하단에서 별도로 유지·제거할 수 있습니다. 일반 Pi/opencode 연결로 자동 이전하거나 기존 명령을 삭제하지 않습니다.

셸 프로필은 자동 수정하지 않습니다. 명령을 찾지 못하면 화면의 전체 경로로 실행하거나, 현재 터미널에서 `export PATH="$HOME/.local/bin:$PATH"`를 실행하세요. 영구 적용은 사용하는 셸의 설정 파일에 직접 추가해야 합니다. 화면의 PATH 감지는 웹 서버 환경 기준이며 터미널 환경과 다를 수 있습니다. 기존 동명 셸 alias·함수는 변경하지 않습니다.

Claude의 기존 Bedrock/Vertex/Foundry 선택 및 클라우드 인증 환경 변수는 전용 실행기 프로세스에서만 제거합니다. OPUS/SONNET/HAIKU/FABLE 별칭은 로컬 Flint로 지정합니다. Codex는 전용 `CODEX_HOME`을 사용합니다. 기존 Pi/opencode 격리 실행기도 전용 설정/데이터 경로를 유지하며, 사용자 모델 목록 연결과는 별개입니다.

**각 CLI의 버전에 따른 실제 호환성은 별도 확인이 필요합니다.** 기본 클라이언트 설정이 합쳐지거나 도구·MCP·텔레메트리가 외부에 접속할 수 있습니다. 모델이 로컬이라는 이유로 클라이언트 전체가 오프라인이 되지는 않습니다. API 요청이 지정한 샘플링 값은 서버 기본값보다 우선하지만 출력 상한은 서버가 제한합니다.

첫 실행 게이트는 넣지 않습니다. Claude 데스크톱 및 ChatGPT Codex 앱 수정, 인증 프록시, macOS 메뉴바, 앱 자동 업데이트, 클라우드 계정 관리는 구현 범위가 아닙니다.

## 제어 경계

제어 HTTP 서버와 inference 서버 모두 `127.0.0.1`에만 바인딩합니다. 제어 서버는 엄격한 Host/Origin 검사, HttpOnly SameSite=Strict 세션, 모든 상태/작업 API의 별도 CSRF 헤더를 요구합니다. mutation은 동일 Origin JSON만 받습니다. CORS·WebSocket·원격 접속·임의 경로/셸 실행 API는 없습니다. 추론 서버는 엄격한 Host, 브라우저 Origin 거부, 독립 로컬 API 토큰을 요구하며 토큰은 브라우저에 전달하지 않습니다.

프로세스는 이 컨트롤러가 직접 생성한 `Popen` 핸들과 프로세스 그룹으로만 종료합니다. PID 파일을 읽어 임의 프로세스를 죽이지 않습니다. 다른 rec 엔진 감지와 포트 충돌은 시작을 거부합니다. 컨트롤러를 SIGKILL하거나 전원이 끊기면 프로세스가 남을 수 있습니다. 다음 실행에서는 다른 엔진으로 감지하여 중복 로드를 거부하며, 이전 세션의 PID를 신뢰해 자동 종료하지 않습니다. 이 경우 터미널에서 실제 프로세스 소유·명령을 확인해 직접 정리해야 합니다.

동일 OS 사용자 권한의 악성 코드, 브라우저 확장, 관리자 권한 공격, 모든 엔진/모델/외부 CLI의 취약점까지 방어하는 보안 제품이 아닙니다. **보안 감사 완료나 100% 안전을 주장하지 않습니다.**

## 개발 / 검증

외부 Python 패키지 설치나 Node 빌드 없이 검증할 수 있습니다.

```sh
python3 -m unittest discover -s tests -v
python3 -m compileall -q flint run.py
node --check static/app.js
node tests/ui_smoke.js
```

화면 이동·시각 효과 원본은 `frontend/src/`에 있습니다. 수정했다면 Node.js 18 이상에서 번들을 다시 만들어 `static/navigation.js`, `static/visuals.js`, `THIRD_PARTY_LICENSES.txt`를 함께 갱신하세요(생성 파일은 직접 편집하지 않습니다):

```sh
cd frontend && npm ci && npm run build
```

테스트는 임시 폴더/가짜 프로세스·측정과 실제 loopback HTTP를 사용합니다. 실제 모델을 자동 실행하거나 실제 클라이언트 설정을 수정하지 않습니다. 실제 추론 검증 및 전체 튜닝 실행 여부는 실행 결과를 별도로 구분해야 합니다. `python3 run.py --help`로 웹 서버 옵션을 확인할 수 있습니다.

설치·모델 준비 및 웹 서버 실행 후, **명시적으로 실제 모델을 구동하는** 수용 검증 명령은 다음과 같습니다:

```sh
python3 -m tests.real_smoke --baseline
```

실제 Chat Completions, Anthropic Messages, Responses 응답 shape와 추론 Host/Origin/토큰 경계를 확인합니다. `--baseline`은 현재 후보 한 개의 전체 측정과 외부 요청 임시 차단, 기존 설정/실행 상태 복원을 확인합니다. 전체 worker/chunk 탐색을 대신하는 검증은 아닙니다. 실제 CLI 설치·실행·클라이언트 전역 설정 변경은 하지 않습니다. 검증 후 서버를 실행 상태로 둡니다.
